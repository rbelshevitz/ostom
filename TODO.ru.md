# OSTOM — план разработки

OSTOM — локальный инструмент восстановления повреждённых Outlook-файлов
`.ost`/`.pst`, работающий только на чтение. Он сохраняет доказательства,
экспортирует всё, что удалось прочитать, не меняет исходный файл и не делает
выводов о полноте серверной копии.

## Текущая база

- Безопасная диагностика заголовка и индексов Unicode-файлов, включая вариант
  со страницами 4 KiB.
- Ограниченный обход NBT/BBT и HN/PC/TC. На реальном OST с вложениями он даёт
  13 кандидатов сообщений из 14 узлов сообщений и связанных сообщений;
  четыре вложения связаны с письмами и восстановлены; каждое сопровождается
  отдельным предупреждением о значении `PidTagAttachSize`.
- Кандидаты вложений сохраняют связь с родительским BID/NID, заявленный и
  фактически прочитанный размер, `Content-ID` и MIME-роль, если эти свойства
  доступны. Объём читаемых данных ограничен.
- Экспорт в Thunderbird `mbox + .sbd`, отдельный экспорт структурно
  восстановленных данных в `mbox` и `.eml`. Ошибка одного письма или вложения
  не останавливает весь экспорт.
- JSON-отчёт, контроль свободного места, ограничители времени и размера,
  а также сведения об источнике каждого кандидата.

## Стратегия тестовых наборов

- [x] Добавить детерминированный Go-генератор корпуса EML в служебную
  утилиту (`ostom-fixture -kind eml`): Unicode-письма, несколько и встроенные
  вложения, стабильные MIME boundary и manifest с SHA-256.
- [ ] Добавить необязательный внешний PST-generator для контролируемых
  фикстур. Держать его вне runtime OSTOM и проверять созданные PST
  независимыми reader'ами; Outlook — дополнительный oracle совместимости, а
  не обязательная зависимость.
- [ ] Не писать PST-writer на Go в составе OSTOM. Текущая Go-зависимость с
  API записи недостаточно надёжна как генератор; создание PST — отдельная
  задача и не должно блокировать восстановление OST.
- [ ] Реальные публичные OST оставить источником доказательств OST-специфики:
  provider/sync-метаданных, локальных папок и сжатых вариантов 4 KiB. PST и
  synthetic OST проверяют только общие пути PFF/MAPI.

## Статус доказательств — 2026-10-18

- [x] Синтетический тест устойчивости проверяет CRC заголовка, заявленный
  размер, обрезанный файл, потерянные корни B-tree и повреждённый служебный
  хвост блока; программа не завершается аварийно.
- [x] На публичном OST проходят проверка заголовка, обход NBT/BBT, XBLOCK и
  дерево subnode и его содержимое.
- [x] Восстановление обрабатывает только NID типов сообщений и не тратит лимит на
  папки и служебные узлы.
- [x] HN/PC-разбор на публичном 4 KiB OST даёт 13 консервативных кандидатов
  сообщений из 14 узлов сообщений и связанных сообщений. Четыре вложения
  связаны с письмами и имеют статус «восстановлено»; ошибок разрешения нет.
  `PidTagAttachSize` больше длины свойства данных, что соответствует
  определению MAPI и само по себе не означает потерю байт.
- [x] Для этого образца подтверждена модель сжатых блоков 4 KiB: BBT хранит
  сжатый размер в `16:18`, а `InflatedSize` — в `18:20`; после распаковки
  содержимое zlib-блока начинается с HN-root. Другие варианты сжатия и шифрования ещё не
  проверены.
- [ ] Полный экспорт всех писем и вложений через текущий CLI пока не доказан.

## Ближайшая очередь работ

- [x] Добавить регрессионную проверку публичного образца: 14 обработанных узлов
  сообщений и связанных сообщений, не менее 13 кандидатов.
- [x] Проверить шаг записей листа subnode для 4 KiB, нормализовать NID до младших
  32 бит, используемых ссылками PC, и рекурсивно обходить вложенные SubBID.
- [x] Разрешить ссылки на данные вложений `0x819F` и `0x827F`: для 4 KiB
  распаковывать сжатую листовую запись по `InflatedSize` из BBT даже при
  наличии признака внутреннего BID.
- [x] Повторно проверить связь вложений с письмами: найдено и связано четыре
  вложения, все имеют статус «восстановлено», ошибок разрешения нет.
- [x] Подтвердить смысл размера: `PidTagAttachSize` включает свойства объекта
  вложения и его нельзя напрямую сравнивать с длиной данных `0x3701`.
- [ ] Только после этого заявлять полный экспорт вложений.

Это уже рабочая база диагностики и экспорта, но ещё не полноценный механизм
восстановления OST. Восстановленные структурным путём элементы могут быть
неполными, дублировать письма из индексированного пути и не иметь надёжного
пути исходной папки.

## Готово означает

На копии настоящего OST OSTOM показывает папки/письма/вложения и их
читаемость, локализует ошибки, экспортирует каждый независимо читаемый объект
в Thunderbird-совместимую иерархию, создаёт воспроизводимую запись
восстановления и никогда не изменяет и не загружает исходник.
