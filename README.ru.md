# ostom

[![CI](https://github.com/rbelshevitz/ostom/actions/workflows/ci.yml/badge.svg)](https://github.com/rbelshevitz/ostom/actions/workflows/ci.yml)
[![Go](https://img.shields.io/badge/Go-1.24%2B-00ADD8?logo=go&logoColor=white)](https://go.dev/doc/install)

> Почтовый археолог для OST/PST: находит читаемые письма и переносит их в любимый почтовый клиент.

`ostom` — утилита на Go для чтения и восстановления Outlook OST/PST в режиме только чтения.
Главная цель — вытащить письма, которые находятся только в локальном хранилище: локальные «Отправленные», «Черновики», «Исходящие», скрытые и нестандартные папки. По одному имени папки программа не решает, что данные серверные.

Требование для сборки: Go 1.24 или новее. Сейчас CI проверяет сборку под
Windows на Go 1.24.x.

OSTOM расшифровывается как **OST Mail Recovery** — «восстановление почты из OST». Это практическое название цели, а не заявление о forensic-возможностях или криптографическом взломе: осмотреть локальное хранилище Outlook, извлечь читаемые элементы, сохранить иерархию папок и выгрузить результат в обычную почтовую программу, например Thunderbird.

Целевой сценарий OSTOM — файлы данных, созданные **классическим Outlook для
Windows**, включая файлы, связанные с Outlook 2016, Outlook 2019, Outlook 2021,
Outlook 2024 и Outlook for Microsoft 365. Это ориентир совместимости, а не
обещание, что каждая редакция, тип учётной записи, вариант файла или
повреждённый файл будет полностью прочитан.

Microsoft, Outlook, Windows, Microsoft 365 и связанные названия являются
товарными знаками группы компаний Microsoft. OSTOM — независимый проект, не
связанный с Microsoft и не одобренный и не спонсируемый Microsoft.

## Быстрый запуск

Если вам нужно просто спасти почту, не обязательно разбираться в формате файла
или собирать исходный код. Скачайте последний [релиз для Windows amd64](https://github.com/rbelshevitz/ostom/releases), закройте Outlook и сделайте копию OST/PST.

1. Проверьте копию и диск назначения:

   ```powershell
   .\ostom.exe --output-dir E:\recovered source-copy.ost
   ```

2. Прочитайте результат в консоли. Если программа рекомендует или требует
   расширенное recovery-сканирование, запустите:

   ```powershell
   .\ostom.exe --recovery-scan --output-dir E:\recovered source-copy.ost
   ```

3. Экспортируйте читаемые письма для Thunderbird:

   ```powershell
   .\ostom.exe --export-dir E:\recovered source-copy.ost
   ```

   Если нужны также результаты расширенного recovery, объедините параметры:

   ```powershell
   .\ostom.exe --recovery-scan --export-dir E:\recovered source-copy.ost
   ```

4. Закройте Thunderbird, скопируйте созданный каталог `Local Folders` в
   каталог `Mail` профиля Thunderbird и запустите программу. До удаления
   исходных данных проверьте восстановленные письма и вложения.

### Перед началом

Сделайте резервную копию OST/PST и запускайте OSTOM на копии. Оригинал
сохраняйте неизменным. OSTOM открывает источник только для чтения, но часть
повреждённых данных может оказаться нечитаемой, поэтому результат не
гарантируется. OSTOM — независимая best-effort утилита восстановления, а не
forensic-система.

Проект намеренно не является forensic-suite. Он не обещает chain of custody, восстановление удалённых записей, взлом паролей, расшифровку DPAPI/EFS/BitLocker или восстановление каждого повреждённого элемента. Исходное хранилище открывается только для чтения, а результат является best-effort.

## Что означает «зашифрованный OST»

В заголовке PFF есть поле `bCryptMethod`. В распространённом формате OST/PST там обычно встречается `None`, `Permute` или `Cyclic` — обратимое кодирование блоков самого формата, а не пароль пользователя и не современное шифрование диска. OSTOM декодирует такие блоки только в памяти: иначе нормальный внешний блок можно ошибочно принять за неизвестный payload. Исходный файл не меняется, расшифрованная копия не создаётся, а DPAPI, EFS, BitLocker и прочие механизмы контроля доступа не обходятся. Неизвестный метод программа сообщает, а не угадывает молча.

## Что умеет OSTOM

OSTOM не объявляется универсальной заменой каждому PFF-reader’у или forensic
системе восстановления. Его практическое отличие — в workflow recovery:

- **Local-first:** физически присутствующие Sent, Drafts, Outbox, скрытые,
  пользовательские и «This computer only» папки считаются ценными.
- **Сначала инспекция, потом извлечение:** evidence по header, allocation,
  NBT/BBT, папкам, письмам, payload и вложениям показывается раздельно.
- **Честное планирование места:** объём экспорта оценивается до долгой работы,
  а нехватка места сообщается явно.
- **Частичный результат — нормальный результат:** один плохой node, письмо или
  attachment не уничтожает читаемую часть; indexed- и recovery-элементы не
  смешиваются молча.
- **Практичность под Windows:** ограничение памяти, честная полоса `N/M`,
  watchdog простоя, JSON и дерево Thunderbird входят в основной workflow.
- **Объяснимая эскалация:** extended recovery рекомендуется только при явном
  evidence, а не из-за одного advisory CRC mismatch.

Это преимущества фокуса и workflow, а не заявление, что OSTOM уже декодирует
больше вариантов PFF, чем зрелые проекты вроде libpff. Native-разбор property,
table и orphan nodes остаётся активной задачей v0.2.

## Сборка и запуск

Установите Go 1.24 или новее и выполняйте команды из корня репозитория. При
первой сборке Go автоматически скачает зависимости, перечисленные в `go.mod`:

```powershell
go build -o ostom.exe ./cmd/ostom
go build -o ostom-fixture.exe ./cmd/ostom-fixture
go test ./...
go vet ./...
```

Запускайте инспекцию на копии исходного файла:

```powershell
.\ostom.exe --output-dir E:\recovered source-copy.ost
```

Экспорт читаемых индексированных писем в дерево, совместимое с Thunderbird:

```powershell
.\ostom.exe --export-dir E:\recovered source-copy.ost
```

В каталоге экспорта появится дерево `Local Folders` с mbox-файлами. Перед
импортом закройте Thunderbird, скопируйте это дерево в каталог `Mail` нужного
профиля Thunderbird и запустите программу — она перестроит индексы папок.
Сохраните резервную копию экспорта, пока не проверите письма и вложения.

### Подпись Windows и SmartScreen

Бинарники релиза пока не подписаны цифровым сертификатом. Поэтому после
скачивания Windows SmartScreen может показать предупреждение «неизвестное
приложение» при запуске `ostom.exe`. Само по себе это предупреждение не
означает, что файл вредоносный. Перед запуском проверьте архив по
опубликованному `SHA256SUMS.txt`; в PowerShell:

```powershell
Get-FileHash .\ostom-v0.2.1-windows-amd64.zip -Algorithm SHA256
```

Администратор может бесплатно подписать внутреннюю сборку собственным или
self-signed Authenticode-сертификатом и установить этот сертификат на
доверенных компьютерах. Это подходит для личного или корпоративного
использования, но не создаёт публичного доверия и не гарантирует исчезновение
SmartScreen на чужих компьютерах. Для публичного распространения обычно нужен
сертификат или signing-сервис доверенного удостоверяющего центра. Закрытый
ключ `.pfx` нельзя публиковать.

### Основные параметры

Основные параметры:

- `--json` — машинно-читаемый отчёт.
- `--output-dir DIR` — том, на котором проверяется свободное место.
- `--export-dir DIR` — экспорт индексированных читаемых писем в дерево Thunderbird `Local Folders`.
- `--recovery-scan` — явно запустить медленный best-effort recovery probe.
- `--memory-limit MB` — мягкий лимит памяти процесса; по умолчанию `256`, `0` отключает.
- `--idle-timeout DUR` — timeout простоя worker; по умолчанию `10m`, `0` отключает.

### Инспекция и recovery

Отчёт может рекомендовать или требовать расширенное recovery-сканирование; `--recovery-scan` остаётся явным параметром, потому что на большом OST он может работать долго.

При совместном использовании с `--export-dir` параметр `--recovery-scan`
также включает у зависимости lenient recovery parser для экспорта. В отчёте
появляется `recovery_mode`; нечитаемые письма и вложения всё равно считаются
ошибками, а не выдаются за успешно восстановленные.

Та же команда дополнительно записывает письма, найденные all-node recovery
iterator, в отдельный mbox `Local Folders\OSTOM Recovered`. Это намеренно
отдельная папка: у recovered-элементов может не быть надёжного исходного пути,
и они могут дублировать обычный indexed export. Исходный node записывается в
`X-Ostom-Source`.

Каталог назначения можно указать уже на этапе инспекции:

```text
ostom --output-dir E:\recovered file.ost
```

Отчёт содержит консервативную оценку размера результата и помечает состояние как `INSUFFICIENT_SPACE`, если на целевом диске места недостаточно. Recovery в таком состоянии должен быть запрещён.

Для более медленного best-effort сканирования узлов восстановления:

```text
ostom --recovery-scan --output-dir E:\recovered file.ost
```

Используется отдельный recovery backend `go-pst`; отчёт показывает число
проверенных, восстановленных, неудачных и orphan-узлов, а также категории
ошибок. Если одновременно указан `--export-dir`, найденные recovery-элементы
записываются отдельно в `Local Folders\OSTOM Recovered`; без `--export-dir`
результат не записывается.

В Windows парсер запускается внутри контролируемого worker-процесса. По
умолчанию worker завершается после 10 минут без heartbeat от обработки
сообщений. Для большого или медленного хранилища лимит можно изменить или
отключить явно:

```text
ostom --idle-timeout 30m file.ost
ostom --idle-timeout 0 file.ost
```

Это timeout простоя, а не общий лимит времени. При timeout исходный файл не
изменяется, а программа возвращает `TIMEOUT`, не выдавая частичный JSON за
успешный отчёт.

### Генератор тестовых fixtures

Для небольшого локального fixture:

```text
go run ./cmd/ostom-fixture -kind pst -out testdata\fixtures\sample.pst
go run ./cmd/ostom-fixture -kind ost -messages 50 -out testdata\fixtures\fifty.ost
go run ./cmd/ostom-fixture -kind pst -damage header-crc -out testdata\fixtures\sample-header-crc.pst
```

`ostom-fixture.exe` — вспомогательная программа для разработчиков и тестов,
а не инструмент восстановления вашей почты. Обычному пользователю нужен
только `ostom.exe`.

Она нужна потому, что разработка и regression-тесты не должны зависеть от
личного повреждённого почтового ящика. Генератор даёт небольшой
воспроизводимый fixture и контролируемые варианты повреждений, чтобы
проверять parser, экспорт, прогресс и recovery без изменения настоящего OST.

Сгенерированный OST — проверенный parser’ом синтетический OST-контейнер, а не архив, созданный Outlook. При `-messages 50` генератор берёт корпус Enron PST, проверяет наличие минимум 50 индексированных писем, меняет PFF client magic, проверяет результат и только потом применяет запрошенное повреждение. Текущий исходный корпус содержит 59 индексированных писем и папки Sent. Его письма и адреса могут быть реальными историческими данными, а не вымышленными персонажами, поэтому корпус и созданные из него fixtures предназначены только для локальных тестов: они не коммитятся и не включаются в релизы. Перед распространением копий нужно проверить условия upstream-корпуса.

### Экспорт в Thunderbird

Для экспорта индексированных читаемых писем в совместимое с Thunderbird дерево `Local Folders`:

```text
ostom --export-dir E:\recovered file.ost
```

Отчёт экспорта содержит полные агрегаты попыток, успешных, частичных и
пропущенных писем, а также ошибок вложений. В JSON есть ограниченная выборка
статусов отдельных писем с исходной папкой и темой; для больших хранилищ
показывается число пропущенных записей, а не создаётся неограниченный список в
памяти.

Вложения связываются через attachment table конкретного письма и копируются потоково через writer `go-pst`. Для inline-вложений сохраняется `Content-ID`, если он есть. Файлы `.msf` не создаются.

### Отчёты, прогресс и ограничения

Он показывает распознавание файла и заголовка, доступ к индексам, обход дерева папок, число писем и непрочитанных, число вложений, заявленный объём вложений и ошибки обхода.

В обычном режиме показывается полоса из 30 символов, `N/M declared`, скорость и elapsed time. Знаменатель собирается до прохода по сообщениям и не скачет назад; `M` — сумма заявленных в таблицах папок количеств, то есть evidence, а не абсолютная истина. Если знаменатель неизвестен, показываются `?`, а не выдуманный процент. Watchdog предупреждает после 60 секунд без прогресса, но не убивает чтение посреди повреждённого node.

Зависимость от парсера намеренно скрыта за интерфейсом `internal/backend`. Для финального восстановления нужны потоковые readers сообщений и вложений; библиотека, материализующая целое вложение в память, не подходит для многогигабайтного OST.

Код OSTOM распространяется по лицензии MIT. Лицензии и attribution зависимостей находятся в `THIRD_PARTY_NOTICES.ru.md`.

## Когда Outlook перестаёт воспринимать базу писем?

Outlook может сломаться на разных уровнях. Сообщения «файл не является файлом данных Outlook» или «невозможно открыть набор папок» сами по себе ещё не показывают, какой уровень неисправен.

| Уровень | Типичная проблема | Что проверяет OSTOM |
|---|---|---|
| Файл/заголовок | обрезанный файл, неправильная `!BDN`/`SO`, неизвестная версия, битый CRC заголовка | сигнатуру, тип, версию, вариант страниц, CRC заголовка там, где он определён |
| Корни/индексы | невалидные корни NBT/BBT или нечитаемая index page | заявленный размер, offsets корней, тип страницы, форму root page |
| Allocation/page | повреждённые AMap/PMap, тип страницы, CRC или back-pointer | известные allocation pages и поддерживаемые footers |
| Дерево папок | не читается hierarchy table или дочерний node | пути папок и structural errors |
| Таблица сообщений | повреждена contents table или message node | читаемые письма и пути папок/писем с ошибками |
| Блок/payload | неправильный размер блока, back-pointer, распаковка или поток вложения | заявленный и реально читаемый payload, ошибки вложений |

Outlook может открыть файл с частичным повреждением, а может отвергнуть его до показа писем. Microsoft отдельно описывает восстановление файла и синхронизации; Sync Monitor может исправлять локальное состояние, запускать scan OST и очищать offline items, после чего начинается полная синхронизация с сервером. [Microsoft Sync Monitor](https://learn.microsoft.com/en-us/microsoft-365-apps/outlook/configuration/sync-monitor-improvements)

Safe Mode — отдельный режим: он отключает COM add-ins и расширения Exchange-клиента. Если Outlook работает только в Safe Mode, вероятной причиной является add-in, но это не доказательство повреждения OST. Это контекст пользователя, а не вердикт о целостности файла. [Диагностика Outlook от Microsoft](https://support.microsoft.com/en-us/outlook/how-to-troubleshoot-performance-issues-in-outlook)

Для Cached Exchange Mode пересоздание OST является штатным способом Microsoft, но опасно как первый шаг, если локальные Sent, Drafts, Outbox или пользовательские папки могут отсутствовать на сервере. [Рекомендации Microsoft по синхронизации](https://learn.microsoft.com/en-us/troubleshoot/outlook/synchronization/synchronization-issues-occur-in-outlook-owa)

Поэтому OSTOM показывает доказательства по уровням, а не возвращает одну необъяснимую метку «битый». Ошибка parser’а остаётся вердиктом «повреждён или вариант не поддержан», пока structural scan не отличит corruption от неподдержанного 4 KiB/compressed-варианта.

### Когда OSTOM рекомендует расширенное recovery-сканирование?

В отчёте есть объяснимый план `deep_recovery`. Значение `required` появляется, когда недоступен нижний слой (ошибка заголовка/заявленного размера, отсутствующие или невалидные корни, ошибка доступа к индексам) либо high-level обход не восстановил ни одного письма при наличии заявленного содержимого. Значение `recommended` появляется только при накопленном сильном evidence: нескольких ошибках чтения/декодирования payload, отсутствующих связях NBT с BBT или существенной доле ошибок сообщений. Одна ошибка parser’а, аномалия allocation map или advisory mismatch trailer/CRC сами по себе эскалацию не включают. Причины также попадают в отчёт.

- Исходный OST/PST не изменяется.
- Быстрый анализ может читать индексированные node-блоки для структурной классификации, но не собирает и не экспортирует attachment streams.
- Заявленный размер вложений отделён от реально прочитанных байт.
- Успешное открытие парсером не считается доказательством полной целостности.
- panic recovery-backend превращается в ошибку отчёта; один битый узел не должен завершать весь инспекционный прогон.
- Экспорт будет сохранять физическую иерархию и принадлежность к хранилищу, включая локальные папки.

Для сборки нужен доступ к Go-модулям. Пока зависимости недоступны локально, можно проверять форматирование и документацию, но нельзя честно заявлять, что полная сборка проверена.

## Отказ от ответственности

OSTOM — независимая best-effort утилита восстановления. Работайте с копией
исходного OST/PST, а не с единственным оригиналом. Результат восстановления
не гарантируется, а успешно открытый отчёт не доказывает, что каждый элемент
файла полностью сохранён.

CLI `ostom` открывает исходное хранилище только для чтения и не отправляет его
содержимое в интернет. Во время инспекции recovery-файлы не создаются. Если
явно указан `--export-dir`, программа создаёт или дописывает совместимые с
Thunderbird файлы только внутри этого каталога. `--output-dir` также может
создать явно указанный каталог, чтобы проверить свободное место. Исходное
хранилище CLI не изменяет. Отдельная утилита разработчика `ostom-fixture`
пишет только в явно указанный путь fixture и во время генерации может создать
рядом временный файл.

OSTOM не связан с Microsoft и не одобрен Microsoft, а также не является
forensic-инструментом. Пользователь отвечает за сохранность оригинала,
проверку экспортированных писем и вложений и соблюдение применимых требований
к приватности и обращению с данными.
